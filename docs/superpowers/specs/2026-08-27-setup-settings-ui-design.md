# Мастер первого запуска и интерфейс настроек

## Цель

Добавить обязательный мастер первого запуска, полноэкранный интерфейс управления базами заметок и безопасное переключение активной базы без перезапуска приложения.

До завершения мастера редактор, дерево и REST-операции с заметками недоступны. После настройки пользователь может создавать, подключать, редактировать, забывать и переключать базы в отдельном экране настроек внутри текущей вкладки браузера.

Git-синхронизация, физическое перемещение баз и удаление пользовательских файлов не входят в эту задачу.

## Состояние первоначальной настройки

В `model.Config` добавляется поле `setup_completed`.

Нужно отличать старый config без этого поля от нового config со значением `false`, поэтому `model.Config` хранит `SetupCompleted *bool`. После загрузки и миграции SettingsService всегда работает с непустым указателем.

Правила миграции:

- существующий непустой config без `setup_completed` считается уже настроенным;
- при запуске в него записывается `setup_completed: true`;
- новый или пустой config создаётся с `setup_completed: false`;
- после успешного мастера сохраняется `setup_completed: true`;
- завершённую настройку нельзя вернуть в состояние `false` через публичный API.

Если существующий клиент отправляет `PUT /api/config` без поля `setup_completed`, текущее состояние setup сохраняется. Явное `false` после завершения настройки отклоняется.

Автоматически созданная база `default` позволяет backend запуститься до мастера, но note API остаётся заблокированным. При завершении мастера placeholder-запись `default` заменяется выбранной базой. Ранее созданный каталог `default` автоматически не удаляется.

## Архитектура backend

### SettingsService

Новый `SettingsService` становится единственной точкой изменения config и активной базы. Он владеет ссылками на `ConfigService` и `NoteService`, сериализует команды через mutex и выполняет:

- миграцию состояния первоначальной настройки;
- завершение мастера;
- создание и подключение баз;
- изменение имени или пути базы;
- забывание неактивной базы;
- переключение активной базы;
- валидированную замену config для совместимости существующего `PUT /api/config`.

HTTP handlers не изменяют config или файловую систему напрямую.

### ConfigService

Сохранение config выполняется через временный файл в том же каталоге. Полностью записанный и закрытый временный файл заменяет основной config. При ошибке исходный config должен сохраниться. Реализация учитывает различия `rename` в поддерживаемых ОС и очищает временный файл после ошибки.

### NoteService

`NoteService` получает блокировку активной базы:

- обычная операция с заметкой удерживает read-lock на всё время обращения к пути базы;
- переключение удерживает write-lock;
- переключение меняет путь, очищает и заново строит SQLite-индекс;
- новые note-запросы ждут завершения переключения;
- запрос, начавшийся раньше переключения, заканчивается на прежней базе;
- `GetBasePath` и `/api/info` всегда возвращают согласованный текущий путь.

Порядок блокировок документируется и остаётся одинаковым для переключения и `SyncFS`, чтобы исключить deadlock.

### Транзакционность переключения

Перед изменением SettingsService проверяет новый config и путь. Затем он переключает и индексирует `NoteService`, после чего атомарно сохраняет config.

Сам `NoteService.SwitchBase` является транзакционным: если индексация новой базы завершилась ошибкой, он возвращает прежний путь и индекс до возврата ошибки. Если сохранение config завершилось ошибкой после успешной индексации, SettingsService повторно переключает `NoteService` на прежний путь и восстанавливает прежний индекс. Ошибка rollback включается в итоговое сообщение и журнал.

При неуспешном создании новой базы автоматически созданный каталог не удаляется: переносимая атомарная проверка «удалить, только если это всё ещё созданный нами каталог» недоступна, а path-based cleanup может удалить подменённый пользовательский объект. Существующие и созданные каталоги, а также пользовательские файлы никогда не удаляются автоматически.

## Блокировка до завершения мастера

До `setup_completed: true` следующие маршруты возвращают `428 Precondition Required` с JSON-кодом `setup_required`:

- `/api/notes`;
- `/api/note`;
- `/api/sync`;
- `/api/raw`;
- `/api/save`;
- `/api/rename`;
- `/api/assets`.

Статика SPA, `/api/config`, `/api/setup`, API управления базами, `/api/system/select-directory` и `/api/info` остаются доступными.

Guard проверяет актуальное состояние SettingsService для каждого запроса. Он не полагается на значение, прочитанное только при запуске.

## REST API

### Получение config

`GET /api/config` возвращает:

```json
{
  "base_dir": "/home/user/.igonotes/bases",
  "bases": [
    {
      "name": "default",
      "path": "/home/user/.igonotes/bases/default",
      "auto_sync": false
    }
  ],
  "current_base": "default",
  "setup_completed": false
}
```

### Завершение мастера

`POST /api/setup` принимает:

```json
{
  "mode": "create",
  "name": "work",
  "path": "/home/user/notes"
}
```

Для `create` поле `path` является родительским каталогом, а итоговый путь равен `<path>/<name>`. Для `connect` поле `path` является точным путём существующей базы.

Успешный ответ содержит сохранённый config и активный путь базы. Повторный вызов после завершения настройки возвращает `409 Conflict`.

### Управление базами

- `POST /api/bases` создаёт или подключает базу с тем же телом `mode/name/path`.
- `PUT /api/bases?name=<старое-имя>` принимает новое `name` и существующий точный `path`.
- `DELETE /api/bases?name=<имя>` забывает неактивную базу без удаления каталога.
- `POST /api/bases/switch` с `{"name":"work"}` переключает активную базу.

Добавление и редактирование неактивной базы не переключает активную базу. Изменение имени активной базы обновляет `current_base`, сохраняя текущий путь. Изменение пути активной базы применяет новый путь через тот же транзакционный механизм, но оставляет экран настроек открытым. Завершение мастера и явная команда `switch` открывают выбранную базу.

### Совместимость config API

`PUT /api/config` сохраняется для ручных инструментов и существующих клиентов, но проходит через SettingsService. Он валидирует весь config, не создаёт каталоги, не разрешает вернуть setup в `false` и безопасно переключает базу, если изменился `current_base` или путь активной базы. Отсутствующее поле `setup_completed` сохраняет текущее значение.

Это правило заменяет поведение из `2026-08-26-runtime-config-base-selection-design.md`, где изменения config применялись только после перезапуска.

### Выбор каталога

`POST /api/system/select-directory` открывает системный диалог и возвращает:

```json
{
  "path": "/home/user/notes"
}
```

Отмена возвращает `204 No Content`. Отсутствие поддерживаемого picker возвращает `501 Not Implemented` с JSON-ошибкой `directory_picker_unavailable`.

## Валидация баз

Общие правила:

- имя после `TrimSpace` непустое;
- имена уникальны и чувствительны к регистру;
- имя создаваемой базы не равно `.` или `..` и не содержит `/` либо `\\`;
- пути сохраняются абсолютными и очищенными через `filepath.Clean`;
- подключаемый и изменённый путь существует и является каталогом;
- родительский каталог новой базы существует и является каталогом;
- итоговый каталог новой базы ещё не существует;
- изменение имени или пути меняет только config и никогда не перемещает каталог;
- активную базу забыть нельзя;
- последнюю базу забыть нельзя;
- забывание базы никогда не удаляет каталог или файлы.

Основные HTTP-статусы:

- `400 Bad Request` для некорректного JSON и отсутствующих полей;
- `404 Not Found` для неизвестной базы;
- `409 Conflict` для повторяющегося имени, существующего пути, удаления активной/последней базы и повторного setup;
- `422 Unprocessable Entity` для некорректного или недоступного пути;
- `428 Precondition Required` до завершения setup;
- `501 Not Implemented` при отсутствии directory picker;
- `500 Internal Server Error` для неожиданных ошибок файловой системы, config или rollback.

Ответы API используют единый JSON-формат с машинным `code`, пользовательским `message` и необязательным `field`.

## Нативный выбор каталога

Backend использует внедряемый command runner, чтобы логику можно было тестировать без открытия настоящих окон.

Порядок выбора:

- Windows: PowerShell и `System.Windows.Forms.FolderBrowserDialog`;
- macOS: `osascript` с `choose folder`;
- Linux: `zenity --file-selection --directory`, затем `kdialog --getexistingdirectory`;
- другие ОС возвращают `directory_picker_unavailable`.

Пользовательский текст не подставляется в shell-команду. Процесс запускается напрямую с фиксированными аргументами. Backend различает успешный выбор, отмену и отсутствие программы.

Текстовое поле пути доступно всегда. Ошибка `directory_picker_unavailable` не блокирует мастер: frontend показывает объяснение и оставляет ручной ввод.

## Архитектура frontend

### App state

`App.svelte` перед монтированием дерева и редактора загружает `/api/config` и показывает одно из состояний:

- экран загрузки;
- обязательный мастер;
- основной редактор;
- полноэкранные настройки.

Настройки являются экраном внутри той же вкладки, а не отдельным окном и не overlay. При первом запуске основной интерфейс вообще не монтируется.

Frontend API-вызовы выносятся из компонентов в небольшой модуль, который нормализует JSON-ошибки и облегчает тестирование.

### Мастер первого запуска

Мастер использует компоновку выбранного варианта C и состоит из трёх шагов:

1. Выбор «Создать новую» или «Подключить существующую».
2. Имя и каталог с ручным вводом и кнопкой «Обзор».
3. Итоговый путь, проверка введённых данных и подтверждение.

Для новой базы шаг 3 показывает вычисленный `<родитель>/<имя>`. Для существующей базы показывается точный выбранный путь.

После успешного `POST /api/setup` frontend получает актуальный config, очищает состояние мастера и монтирует редактор с выбранной базой. Назад из незавершённого мастера в редактор перейти нельзя.

### Экран настроек

Экран открывается кнопкой с шестерёнкой в header редактора. Перед переходом App отменяет debounce и немедленно сохраняет активную заметку. При ошибке сохранения настройки не открываются. Кнопка «Назад к заметкам» возвращает основной интерфейс.

Навигация содержит:

- активный раздел «Базы заметок»;
- отключённый раздел «Git, скоро».

Раздел баз показывает карточки с именем, путём и признаком текущей базы. Доступны действия:

- «Открыть» для неактивной базы;
- «Изменить»;
- «Забыть» для неактивной базы, если баз больше одной;
- «Добавить базу».

Формы добавления и редактирования используют ту же визуальную систему и validation, что и мастер. Git URL и автосинхронизация отображаются отключёнными и не изменяются.

### Сохранение перед переключением

Перед `POST /api/bases/switch` App повторно проверяет отсутствие несохранённых изменений и при необходимости выполняет немедленное сохранение. При ошибке сохранения переключение не отправляется, настройки остаются открыты и показывают ошибку.

После успешного переключения frontend:

- очищает активную заметку и содержимое редактора;
- обновляет config и путь status bar;
- закрывает настройки;
- монтирует новое дерево, которое загружает данные выбранной базы.

### Адаптивность и доступность

На широком экране настройки используют левую навигацию и правую рабочую область. На узком экране навигация становится верхними вкладками, а формы и карточки переходят в одну колонку.

Мастер и настройки поддерживают keyboard navigation, видимый focus, связанные `label`, `aria-current`, `aria-disabled`, сообщения об ошибках и перевод фокуса на первое ошибочное поле. Нативная отмена picker не считается ошибкой.

## Ошибки frontend

Ошибки полей показываются непосредственно под полем. Конфликты операций отображаются внутри соответствующей карточки или формы. Неожиданные ошибки показываются общей панелью в рабочей области.

Пользовательский ввод сохраняется после ошибки. Компоненты не ограничиваются `console.error` для пользовательски значимых сбоев.

Если первоначальная загрузка config завершилась ошибкой, приложение показывает блокирующий экран с сообщением и кнопкой повторной попытки, а не открывает редактор.

## Тестирование

### Backend

Тесты покрывают:

- миграцию старого config в `setup_completed: true`;
- создание нового config с `setup_completed: false`;
- невозможность вернуть завершённый setup в `false`;
- блокировку всех note API через `428`;
- успешное создание и подключение базы;
- validation имён и путей;
- запрет удаления активной и последней базы;
- отсутствие физического удаления забытой базы;
- атомарное сохранение и сохранность исходного config при ошибке;
- успешное live-переключение и переиндексацию;
- изменение имени и пути активной базы;
- откат пути и индекса при ошибке синхронизации или сохранения;
- конкурентный note-запрос во время переключения;
- системный picker для каждой ОС через fake command runner;
- отмену picker и отсутствие поддерживаемой программы;
- HTTP statuses и JSON-коды ошибок.

### Frontend

Добавляется Vitest и Svelte component testing. Тесты покрывают:

- блокирующий мастер при `setup_completed: false`;
- отсутствие Sidebar и Editor до завершения setup;
- переходы трёх шагов;
- validation и сохранение введённых значений после ошибки;
- ручной fallback при `directory_picker_unavailable`;
- загрузку и отображение баз;
- отключённый раздел Git;
- запрет забывания активной и последней базы;
- сохранение заметки перед открытием настроек;
- немедленное сохранение заметки перед переключением;
- отмену переключения при ошибке сохранения;
- очистку состояния и возврат в редактор после переключения.

### Итоговая проверка

- `go test -race ./...`;
- `go vet ./...`;
- frontend unit/component tests;
- `make all`;
- first-run smoke test с изолированными `HOME` и `XDG_CONFIG_HOME`;
