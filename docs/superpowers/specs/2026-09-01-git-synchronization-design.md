# Git-синхронизация баз заметок

## Цель

Добавить в IGoNotes опциональную Git-интеграцию для каждой базы заметок. Она должна поддерживать двустороннюю синхронизацию нескольких устройств через один remote `origin` и выбранную ветку, ручные и фоновые циклы синхронизации, безопасное первичное объединение существующей базы с существующим репозиторием и разрешение конфликтов в интерфейсе IGoNotes.

Git не становится обязательным способом хранения. Обычный каталог с Markdown-файлами остаётся полноценной базой и работает без установленного `git`, сетевого доступа и Git-настроек.

## Основные решения

- Используется системный исполняемый файл `git`, а не встроенная Go-библиотека.
- Каталог базы должен точно совпадать с корнем Git-репозитория.
- Для каждой базы настраиваются URL `origin`, ветка, частота полного sync и шаблон локального commit message.
- Источник правды после подключения — граф commit выбранной ветки, а не безусловно локальный каталог или remote.
- Непересекающиеся изменения объединяются обычным Git merge.
- Конфликты никогда не разрешаются автоматическим выбором стороны.
- Перед первым объединением существующих данных создаются локальный commit и страховочный ref.
- Force-push, rebase, reset чужой истории и автоматическое удаление Git-данных запрещены.
- После пяти последовательных операционных ошибок autosync приостанавливается до явного действия пользователя.

## Не входит в первую версию

- хранение HTTPS-токенов или SSH-ключей в IGoNotes;
- автоматическая установка или обновление Git;
- несколько remote для одной базы;
- база как подкаталог monorepo;
- rebase, squash, force-push и автоматическое исправление переписанной remote history;
- управление Git LFS и submodules;
- настройка интерактивной подписи commit;
- системные desktop-уведомления и web push;
- cron-выражения и произвольные интервалы autosync.

## Опциональность и совместимость

База без полной Git-настройки работает как до этого изменения. Backend не проверяет наличие системного Git, не создаёт `.git` и не запускает Git-команды, пока пользователь явно не настраивает интеграцию или не вызывает Git API.

Наличие `.git` в каталоге само по себе не включает интеграцию. Это позволяет использовать внешний Git-клиент без автоматических действий IGoNotes.

Существующие поля `git_url` и `auto_sync` в `model.Base` сохраняются. Модель дополняется:

```json
{
  "name": "work",
  "path": "/home/user/notes/work",
  "git_url": "git@github.com:user/work-notes.git",
  "git_branch": "main",
  "auto_sync": true,
  "auto_sync_interval_minutes": 15,
  "git_commit_message_template": "IGoNotes: sync {{base}} at {{datetime}} ({{count}} files)"
}
```

Git считается настроенным только после успешного сохранения непустых `git_url` и `git_branch` через Git-настройки. Старый config с одним `git_url` не активирует интеграцию автоматически. Значение `auto_sync: false` отключает расписание, но не ручной sync.

Поддерживаются интервалы `5`, `15`, `30` и `60` минут. При выключенном autosync сохранённый интервал может оставаться в config и используется при следующем включении.

Отключение интеграции очищает Git-настройки базы и останавливает её задачи, но не удаляет `.git`, remote, refs, commits или пользовательские файлы. Забывание базы также только останавливает её задачи и удаляет служебный статус IGoNotes.

Если путь Git-настроенной базы изменяется, autosync атомарно приостанавливается со статусом `needs_reconnect`. Новый каталог должен пройти probe и явное повторное подключение; старые настройки никогда не применяются к новому пути автоматически. Изменение имени при неизменном пути сохраняет интеграцию.

Две Git-настроенные базы не могут указывать на один канонический каталог с разными настройками. Попытка возвращает `409 git_repository_in_use`.

## Системный Git и авторизация

Backend запускает `git` напрямую через `exec.CommandContext`, без shell и построения командной строки из пользовательского ввода.

Git использует обычную пользовательскую инфраструктуру:

- global/local Git config;
- credential helper;
- SSH-agent и `known_hosts`;
- системные настройки proxy и TLS.

Все фоновые команды получают `GIT_TERMINAL_PROMPT=0` и ограничивают transport protocols через `GIT_ALLOW_PROTOCOL=file:http:https:ssh:git`. Авторизация, требующая интерактивного prompt, завершается диагностируемой ошибкой. Допускаются только HTTP(S), SSH, Git, file, scp-like и локальные пути; remote helpers вида `ext::` и произвольные `<helper>::<address>` отклоняются. URL HTTP(S), содержащий userinfo, password или token, не принимается. Ошибки и журналы очищаются от URL и возможных секретов.

Минимальная поддерживаемая версия — Git 2.28. Перед подключением проверяются версия, доступность remote, выбранная branch и commit identity. Имя ветки валидируется самим Git через `check-ref-format`.

Git hooks и системные настройки соблюдаются во всех изменяющих worktree фазах под блокировкой. Если commit signing или commit/merge hook требуют интерактивного ввода, команда завершается ошибкой. Единственное явное исключение — `pre-push`: push запускается с `--no-verify` после освобождения блокировки редактора, чтобы внешний hook не мог параллельно изменить базу заметок.

## Архитектура backend

### GitCommandRunner

`GitCommandRunner` является единственной точкой запуска Git-процессов. Он отвечает за:

- аргументы без shell;
- рабочий каталог, равный каноническому пути базы;
- context cancellation и отдельные timeout для сетевых и локальных операций;
- неинтерактивное окружение;
- ограничение сохраняемого stdout/stderr;
- очистку секретов;
- преобразование exit status и известных сообщений Git в структурированные ошибки.

Runner не принимает готовую shell-строку. URL, branch и path всегда передаются отдельными аргументами после валидации.

### GitService

`GitService` выполняет одну конечную операцию над одним репозиторием:

- probe локального каталога и remote;
- initialize/connect;
- чтение status и ahead/behind;
- один sync cycle;
- чтение conflict stages;
- применение одного решения;
- complete или abort merge;
- восстановительная проверка после restart или отменённой команды.

Сервис не планирует задачи и не изменяет application config.

### GitManager

`GitManager` владеет очередью, расписанием и runtime-статусом всех настроенных баз. Для одной базы одновременно существует не более одной задачи. Повторный ручной запрос возвращает идентификатор текущей операции вместо создания дубля.

Задачи разных баз выполняются последовательно. Их начальные моменты слегка разнесены, чтобы не запускать несколько credential/network процессов одновременно.

Manager получает immutable snapshot настроек, а перед изменением рабочего дерева повторно проверяет имя, путь и актуальность Git-конфигурации. Он хранит progress, последнее безопасное сообщение, changed paths и operation ID.

### SettingsService

`SettingsService` остаётся единственным владельцем application config. Он получает отдельные команды настройки и отключения Git. Обычное добавление базы не запускает сетевые операции и не включает Git.

Probe не изменяет config или файловую систему. Сохранение Git-настроек и initialize/connect разделены: после успешной синтаксической проверки настройки сохраняются, затем асинхронная задача выполняет подключение. Если между probe и задачей изменились сеть, credentials или remote, config остаётся доступным для исправления, а база получает статус `error`.

### Координация с NoteService

Общий coordinator сериализует Git-операции с изменением/забыванием базы и переключением активного пути.

Для активной базы GitManager вызывает эксклюзивную filesystem-транзакцию `NoteService`. Локальные `git add`, commit, merge, запись conflict resolution и перестроение SQLite-индекса выполняются под write-lock активной базы. Обычные note-запросы ждут её завершения.

Сетевой fetch выполняется до этого write-lock, потому что он не меняет рабочее дерево. Push выполняется после успешного merge и переиндексации, чтобы не блокировать редактор на время сети. Coordinator остаётся занятым до конца Git-задачи, поэтому база не может переключиться или сменить путь в середине операции.

Для неактивной базы Git-операция не блокирует редактор текущей базы. Coordinator не позволяет переключиться на синхронизируемую базу, пока её рабочее дерево меняется.

Порядок lock документируется и остаётся единым: coordinator, затем блокировка активной базы, затем repository/SQLite. GitService и repository не вызывают обратные слои.

## Операционный статус

Публичные состояния базы:

- `unconfigured` — Git не настроен;
- `initializing` — создаётся или подключается repo;
- `ready` — задача не выполняется и блокирующей ошибки нет;
- `syncing` — выполняется Git-задача;
- `error` — последняя задача завершилась ошибкой, но лимит не достигнут;
- `paused` — circuit breaker остановил autosync;
- `conflict` — есть незавершённый merge;
- `needs_reconnect` — изменился путь или обнаружено несовпадение repo/origin.

Status дополнительно содержит operation ID, этап, ahead/behind, число последовательных ошибок, время последней попытки, время последнего успеха, список затронутых путей и безопасную структурированную ошибку.

Последний успех, error counter и состояние circuit breaker сохраняются в служебной SQLite-базе по каноническому пути repo. Они не смешиваются с пользовательским config и переживают restart. Незавершённый merge является состоянием самого Git-репозитория и восстанавливается по `MERGE_HEAD` и unmerged index entries.

## Probe и настройка

Настройка выполняется в четыре шага:

1. Ввод URL `origin` и неинтерактивная проверка Git/авторизации.
2. Анализ локального каталога и remote, затем выбор существующей remote branch. Для пустого remote пользователь задаёт новую branch.
3. Выбор ручного режима или интервала и ввод commit template с preview.
4. Review всех мутаций и предупреждений с явным подтверждением.

Probe возвращает:

- есть ли `.git` и совпадает ли repo root с базой;
- текущую branch и состояние working tree;
- URL существующего `origin`;
- список remote branches и признак пустого remote;
- наличие незавершённой Git-операции;
- необходимость создать repo, добавить/заменить `origin`, создать branch или объединить истории;
- предупреждение, что commit включает все неигнорируемые файлы базы.

Если existing `origin` отличается, его замена требует отдельного boolean-подтверждения в mutation request. Если repo root является родительским каталогом базы, подключение отклоняется.

Незавершённые merge, rebase, cherry-pick или revert не изменяются автоматически. Настройка блокируется и предлагает сначала завершить операцию во внешнем Git-клиенте либо использовать доступный в IGoNotes recovery для merge-конфликта.

## Первичное подключение

### Общие гарантии

Перед объединением существующего локального дерева с remote все неигнорируемые локальные изменения фиксируются commit. Текущий commit сохраняется под `refs/igonotes/backups/<UTC timestamp>`. Ref локальный и автоматически не отправляется.

Подключение не использует force-push и не удаляет локальные или remote commits. Push выполняется только после успешного объединения.

Если задача успела создать `.git`, remote, branch, commit или backup ref, а затем завершилась ошибкой, созданные Git-данные не удаляются автоматически. Повторный запуск сначала инспектирует фактическое состояние и продолжает идемпотентно.

### Каталог без repo, пустой remote

IGoNotes выполняет `git init`, создаёт выбранную branch, добавляет `origin`, фиксирует все неигнорируемые файлы и отправляет branch. Если коммитить нечего, разрешён единственный служебный empty initial commit, чтобы создать branch на remote. Плановые sync никогда не создают empty commits.

### Каталог без repo, существующая remote branch

Если локально нет коммитируемых файлов, branch создаётся из remote branch и её дерево checkout-ится в базу.

Если локальные файлы есть, они сначала фиксируются в локальной истории и backup ref. Затем выполняются fetch и merge remote branch с `--allow-unrelated-histories`. Непересекающиеся пути образуют объединённое дерево. Пересечения переходят в обычный conflict workflow.

### Существующий repo

Корень repo обязан совпадать с базой. Все локальные изменения сначала фиксируются. Если выбранная branch отличается от текущей, текущий snapshot сохраняется backup ref, затем выбранная локальная или remote branch checkout-ится, а snapshot объединяется merge. Detached HEAD не используется как рабочий режим.

Отсутствующий `origin` добавляется. Отличающийся `origin` заменяется только после явного подтверждения. Existing branch объединяется обычным merge. Новая branch допускается автоматически только для пустого remote.

## Обычный sync cycle

Один полный цикл выполняет:

1. Проверить config, repo state, circuit breaker и отсутствие конфликта.
2. Выполнить `fetch origin <branch>` без изменения рабочего дерева.
3. Под эксклюзивной блокировкой активной базы выполнить `git add -A`.
4. Создать локальный commit только при наличии staged changes.
5. Объединить полученную remote branch обычным merge без rebase.
6. Если рабочее дерево изменилось, перестроить SQLite-индекс до освобождения блокировки.
7. Освободить блокировку редактора и выполнить push выбранной branch в `origin`.
8. При non-fast-forward из-за одновременного remote push один раз повторить fetch/merge/push.
9. Сохранить status, changed paths и результат.

`git add -A` охватывает всё рабочее дерево и уважает `.gitignore`. Это включает Markdown, `assets`, удаления и любые другие неигнорируемые файлы. Config IGoNotes и metadata SQLite находятся вне базы и не попадают в commit.

Если локальных и remote изменений нет, цикл не создаёт commit. Если remote только впереди, допускается fast-forward. Если стороны разошлись, создаётся merge commit. Удаления распространяются обычной Git-семантикой.

Push после освобождения note lock отправляет конкретный уже созданный commit. Новые пользовательские изменения, возникшие параллельно с push, остаются в working tree до следующего цикла и не теряются.

## Commit message

Пользовательский template применяется только к локальному autosync/manual-sync commit. Поддерживаются переменные:

- `{{base}}` — текущее имя базы;
- `{{branch}}` — выбранная branch;
- `{{date}}` — локальная календарная дата в формате `YYYY-MM-DD`;
- `{{datetime}}` — локальное время RFC 3339 с часовым поясом;
- `{{count}}` — число staged paths.

Template является одной строкой длиной от 1 до 200 символов. NUL, перевод строки и неизвестные переменные отклоняются. UI показывает preview до сохранения.

Значение по умолчанию:

```text
IGoNotes: sync {{base}} at {{datetime}} ({{count}} files)
```

Initial и merge commits используют отдельные стабильные системные сообщения. Пользовательский template не применяется к ним.

## Защита открытого редактора

Filesystem lock не защищает текст, который ещё находится в браузере. Поэтому `GET /api/note` дополнительно возвращает SHA-256 revision текущих байтов файла:

```json
{
  "id": "notes/idea.md",
  "content": "# Idea\n",
  "revision": "sha256:..."
}
```

Новый frontend отправляет `expected_revision` в `POST /api/save`. Backend под lock повторно читает файл и сравнивает revision перед записью. При несовпадении он возвращает `409 note_changed`, не изменяя файл. После успешной записи ответ содержит новую revision.

Для совместимости существующий клиент может не передавать `expected_revision`; такой запрос сохраняет прежнюю unconditional-семантику API. Официальный frontend всегда использует revision.

При `note_changed` пользовательский buffer остаётся в памяти. UI позволяет:

- загрузить актуальный файл с диска;
- подтвердить перезапись своей версией после получения актуальной revision;
- вручную объединить оба текста.

Frontend периодически читает Git status активной базы. После успешного sync backend сообщает changed paths:

- открытая чистая заметка, попавшая в changed paths, перечитывается автоматически;
- грязная заметка не перечитывается и показывает предупреждение/сравнение;
- несколько вкладок защищены тем же revision-механизмом.

Ручной Git sync сначала вызывает существующий `flushWorkspace()`. Фоновый sync не ждёт браузер, но revision не позволяет позднему autosave молча затереть полученное изменение.

## Git-конфликты

Если merge оставляет unmerged entries, push не выполняется. Autosync этой базы приостанавливается немедленно, без расходования пяти попыток circuit breaker. Обычные create/save/rename/delete для конфликтной базы возвращают `409 git_conflict_pending`.

Чтение файлов остаётся доступным для восстановления, но официальный frontend переводит активную базу в отдельный conflict workspace. Переключиться на другую базу можно после завершения текущей Git-команды; конфликт остаётся сохранённым в неактивном repo.

Conflict workspace показывает пути и Git stages с пользовательскими названиями «Общий предок», «На этом устройстве» и «В репозитории».

Поддерживаемые решения:

- текст: локальная версия, remote-версия или вручную отредактированный результат;
- binary/assets: локальная версия, remote-версия или обе версии под разными именами;
- modify/delete: сохранить выбранное содержимое либо подтвердить удаление;
- rename/delete и add/add: выбрать итоговые пути и содержимое.

Каждое решение записывается и stage-ится отдельно. Complete доступен только при отсутствии unmerged entries. Он создаёт merge commit, перестраивает SQLite-индекс и выполняет push.

Действие «Отложить» выполняет `git merge --abort`, восстанавливает локальный snapshot и переводит базу в `paused`. Remote остаётся необъединённым; следующий sync запускается только после явного «Повторить и возобновить».

После restart GitManager обнаруживает `MERGE_HEAD` и unmerged entries. Уже stage-нутые решения сохраняются. IGoNotes никогда автоматически не выбирает сторону конфликта и не удаляет lock/state files вручную.

## Autosync и circuit breaker

Autosync запускается для всех баз с `auto_sync: true`, включая неактивные. После старта backend задачи ставятся в последовательную очередь с небольшим разнесением, затем запускаются каждые 5, 15, 30 или 60 минут относительно последней попытки.

Для каждой базы ведётся число последовательных неудачных sync cycles:

- успешный sync сбрасывает счётчик в `0`;
- операционная ошибка увеличивает его на `1`;
- после пятой последовательной ошибки состояние становится `paused`;
- validation error до постановки sync, shutdown cancellation и пользовательский abort не увеличивают счётчик;
- merge conflict сразу устанавливает `conflict` и не повторяется автоматически.

В `paused` scheduler не ставит новые задачи. UI показывает постоянное сообщение с причиной, временем последней попытки и действиями «Повторить и возобновить» и «Открыть настройки». Событие также записывается в application log.

«Повторить и возобновить» и изменение Git-настроек сбрасывают breaker и ставят одну задачу. После следующих пяти последовательных ошибок база снова приостанавливается.

При закрытом UI pause сохраняется. Пользователь видит уведомление при следующем открытии; отдельное системное уведомление не отправляется.

## Timeout, отмена и неизвестный результат

Network timeout отменяет Git-процесс через context. Локальные commits не откатываются и могут быть отправлены следующей попыткой.

Timeout push может иметь неизвестный результат: remote мог принять commit до разрыва соединения. Следующий цикл всегда начинает с fetch/status и сравнивает OID, поэтому не создаёт дубликат commit и распознаёт уже успешный push.

После timeout локальной операции GitService инспектирует repo state. Если обнаружен незавершённый merge, база переходит в `conflict`; если найден lock другого живого процесса или неоднозначное состояние, операция останавливается с безопасной ошибкой. IGoNotes не удаляет `.git/index.lock` автоматически.

Graceful shutdown отменяет сетевые команды, сохраняет status и не запускает скрытый финальный commit.

## Переписанная история и другие ошибки

Основные машинные коды:

- `git_unavailable`;
- `git_version_unsupported`;
- `auth_failed`;
- `remote_unreachable`;
- `identity_missing`;
- `invalid_branch`;
- `branch_deleted`;
- `origin_mismatch`;
- `repository_root_mismatch`;
- `repository_locked`;
- `remote_history_rewritten`;
- `push_rejected`;
- `git_conflict_pending`;
- `note_changed`;
- `git_repository_in_use`.

Protected branch или временный rejected push оставляет локальные commits и состояние ahead. Удаление remote branch и non-fast-forward перемещение remote branch относительно последнего сохранённого remote OID не исправляются автоматически. База приостанавливается и требует явного выбора пользователя или внешнего Git-клиента. Force-push из IGoNotes недоступен.

Ошибки обычного Git sync не блокируют редактор, если рабочее дерево осталось согласованным. Конфликт или неоднозначная незавершённая локальная операция блокируют только мутации соответствующей базы.

## REST API

Все Git routes проходят существующие local-origin и setup guards.

### Probe

`POST /api/git/probe` принимает имя базы и кандидатные URL/branch. Он не изменяет config, `.git` или remote и возвращает локальное состояние, branches и список требуемых подтверждений.

### Конфигурация

`PUT /api/git/config?base=<name>` принимает URL, branch, autosync, интервал, template и явные подтверждения probe. Ответ содержит сохранённый config, operation ID и `202 Accepted`, если поставлена initialize/connect задача.

`DELETE /api/git/config?base=<name>` отключает интеграцию и очищает её application-настройки. Git-данные на диске остаются.

### Status и запуск

`GET /api/git/status` возвращает status всех баз. Необязательный `base` фильтрует ответ.

`POST /api/git/sync?base=<name>` ставит ручной sync и возвращает `202 Accepted`. Если задача уже выполняется, возвращается её operation ID. При `conflict`, `paused` или `needs_reconnect` API возвращает `409` и соответствующий code; resume является явным отдельным действием.

`POST /api/git/resume?base=<name>` сбрасывает circuit breaker и ставит одну задачу.

### Конфликты

- `GET /api/git/conflicts?base=<name>` возвращает conflict paths, stages и допустимые действия.
- `PUT /api/git/conflicts/resolve` применяет одно решение.
- `POST /api/git/conflicts/complete?base=<name>` завершает merge и ставит push.
- `POST /api/git/conflicts/abort?base=<name>` откладывает конфликт через merge abort.

Conflict API не принимает абсолютные пути. Все относительные пути проходят ту же root/path validation, что note API.

### Ошибки

Ответы используют существующий объект `code/message/field`; endpoints со статусом и конфликтами возвращают дополнительные структурированные данные в успешных payload. Пользовательский stderr Git напрямую в API не возвращается.

## Frontend

### Настройки

Отключённая вкладка «Git, скоро» становится рабочим разделом. Она показывает все базы и их статусы. Git не включается в setup wizard или `BaseForm`: пользователь сначала создаёт/подключает обычную базу, затем отдельно настраивает Git.

Настройка состоит из URL/probe, выбора branch, расписания/template и review. Замена `origin`, создание `.git`, создание branch и объединение несвязанных историй показываются как отдельные последствия до подтверждения.

Template имеет live preview и подсказку по разрешённым переменным.

### Статус

Карточка базы показывает `Git не настроен`, `Синхронизировано`, `Есть локальные изменения`, `Выполняется`, `Ошибка`, `Приостановлено` или `Конфликт`.

Для текущей базы компактный индикатор появляется в нижнем status bar редактора. Он открывает детали и позволяет запустить manual sync. Существующая кнопка `/api/sync` продолжает только пересканирование ФС/SQLite и называется «Обновить дерево».

Frontend polling получает operation progress, changed paths и persisted pause. При достижении пяти ошибок показывается постоянный alert, а не исчезающий toast.

### Конфликты и stale editor

Conflict workspace блокирует обычное редактирование соответствующей базы, сохраняет фокус и пользовательский ввод между API-ошибками, поддерживает keyboard navigation и явно маркирует локальную/remote стороны.

Dialog `note_changed` сохраняет грязный buffer и не выполняет автоматическую перезапись. Выбор «Оставить мою версию» требует отдельного подтверждения.

## Безопасность и файловая модель

- Все Git paths привязаны к каноническому корню базы.
- Repo root должен совпадать с базой; parent repo не допускается.
- Git может отслеживать symlink-файлы, но note scanner продолжает их игнорировать.
- `.gitignore` определяет исключения; дополнительные скрытые include/exclude правила IGoNotes не вводит.
- Пользователь предупреждается, что `git add -A` включает все неигнорируемые файлы, включая файлы, не показанные в дереве заметок.
- `.git` уже исключён из note scanner.
- Config и metadata DB находятся вне базы.
- Remote не обязан быть GitHub; поддерживаются HTTP(S), SSH, Git, file, scp-like и локальные пути, с которыми работает системный Git без prompt. Remote helpers и протоколы вне явного allowlist не поддерживаются.

Git integration suite выполняется в CI на Linux, Windows и macOS с Git 2.28 или новее.

## Критерии готовности

- База без Git ведёт себя как раньше и не требует установленного `git`.
- Git включается и отключается отдельно для каждой базы.
- Два устройства обмениваются непересекающимися изменениями через выбранную branch.
- Существующие локальные и remote данные безопасно объединяются после создания backup ref.
- Конфликт, timeout, restart и rejected push не приводят к silent overwrite или force-push.
- Stale browser save получает `409 note_changed` и не затирает входящее изменение.
- После изменения рабочего дерева SQLite и frontend показывают согласованное дерево.
- После пяти последовательных ошибок autosync прекращается, pause переживает restart и виден пользователю.
- Незавершённый конфликт переживает restart и разрешается в UI.
- Секреты не попадают в config, API, log или commit message.
- `go test ./...`, `go test -race ./...`, frontend tests и production build проходят.
